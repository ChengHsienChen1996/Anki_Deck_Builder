# 實驗：重拍照片能不能修好「小寫假名與濁點讀不出來」

建立日期：2026-09-11
狀態：**兩輪都已執行（2026-09-12），照片路線實測否決**——重拍 41 頁不值得，改走形態素分析器修正。見本檔末〈第二輪實測結果〉之〈五〉
腳本：`scripts/ab-photo-quality.py`

---

## 要回答的問題

**照片品質是不是 OCR 讀不出小寫假名與濁點的原因？**
是的話值得把 41 頁全部重拍；不是的話重拍是白費工，該把力氣放在別處。

---

## 已知的事實（2026-09-11 量測，不必重做）

### 1. 錯誤源自 OCR，不是抽取階段

65 筆 `marks` 類讀音錯誤中，**61 筆（94%）的正確讀音從未出現在該頁 `raw_text`**。
OCR 就沒讀到。（另外 4 筆是 OCR 讀對、抽取階段改壞的，與照片無關。）

### 2. 錯誤形態高度集中

```
がいろじゆ ← がいろじゅ      きゆう   ← きゅう
かつりよく ← かつりょく      きよか   ← きょか
きみよう  ← きみょう        きょきょう ← ぎょぎょう（濁點漏掉）
```

全部是**小寫假名被讀成大寫**與**濁點消失**——差別只在字的大小與兩個小點。
這是細節解析不足的典型指紋。

### 3. 解析度不是瓶頸

| | 量到的值 | OCR 通常需要 |
|---|---|---|
| 文字行高 | 243–259 px | — |
| 假名注音字高 | 約 60–80 px | 20–30 px |
| 小寫假名字高 | 約 40 px | 20–30 px |

**再加像素不會有幫助。** 41 頁全部在 23–42 MP。
（2026-09-12 補：這條只說「往上加沒用」，**不代表往下砍沒差**。第一輪重拍誤用 12MP 模式掉到 6–7 MP，小寫假名只剩約 16 px，落到門檻以下。）

### 4. 但頁與頁之間的品質差異，預測不了錯誤數

| 指標 | 與 `marks` 錯誤的相關係數 |
|---|---|
| 文字區銳利度（原始解析度） | −0.27 |
| 筆畫對比 | −0.28 |
| 糊邊比 | −0.16 |

而且**最銳利的 1/3（14 頁）平均 1.6 筆錯誤，最模糊的 1/3 平均 1.2 筆**——方向反了。

**原因是這批照片太一致**：糊邊比 40 頁落在 0.48–0.69 的窄帶內，
資料裡沒有「好照片」可以對照。所以**現有資料證不出也否證不了**照片假說，
只能人工重拍幾頁做對照。

### 5. 分塊修好後 OCR 的貢獻已大幅提升

卡片 `reading` 能在 `raw_text` 找到的比例：**28% → 74%**
（28% 是 CLAUDE.md 記的分塊前基準 97/342）。剩下的就是這個特定弱點。

## 拍攝條件

量測顯示這批照片有兩處具體缺陷，**同一批裡的 p41 證明這些數字拍得出來**：

| 缺陷 | 全批現況 | p41 達到 | 腳本的門檻 |
|---|---|---|---|
| 曝光不足，紙面偏灰 | 紙面亮度中位數 **190**/255 | **252** | 240 |
| 筆畫對比低 | 中位數 **130** | **199** | 170 |

另外**每一頁都有背面文字的紫色鬼影**（背面透光），那會給 OCR 加上不存在的筆畫。

> ⚠️ **2026-09-12 補：上表那兩個門檻（240／170）已實測降級，不要照著追。**
> 它們當初只是「同批的 p41 碰巧達到過」，從未驗證為因果——而〈已知的事實〉第 4 條
> 本來就說了這類品質指標預測不了錯誤數。第二輪把兩項都做到達標（250／242），
> OCR 結果反而是三組裡最差的。**唯一實測有效的是對焦（銳利度）**，
> 曝光補償本身則因為與後製綁在一起，這兩輪都沒單獨測到。

重拍 **p22 與 p19** 這兩頁，條件：

1. **光線加足**，讓紙面接近純白（目標亮度 240+）。這同時解決曝光、快門與景深
2. **頁面下墊一張黑色不透光紙**，擋掉背面透光
3. **相機固定**（腳架，或撐在桌面／書堆上），鏡頭與頁面平行，避免手持晃動
4. 其餘不變：同一本書、同樣的框取範圍、不要裁切

> 為什麼選這兩頁：p22 有 6 筆、p19 有 3 筆 `marks` 錯誤，是全書錯誤最密集的兩頁
> （p9 有 8 筆但那頁的錯誤形態較雜）。共 9 個目標，樣本夠小又夠看得出差別。

## 一、重拍的照片只修好四項條件裡的一項

| 指標 | p19 舊 → 新 | p22 舊 → 新 | 判定 |
|---|---|---|---|
| 銳利度 | 12.8 → **208.3** | 25.1 → **132.7** | ✅ 手震／失焦確實修掉了，十倍以上 |
| 解析度 | 38.7 → **6.1 MP** | 30.8 → **7.4 MP** | ❌ 線性尺寸只剩 2.4 分之一 |
| 紙面亮度（目標 240） | 190 → 187 | 191 → 194 | ❌ 完全沒動 |
| 對比（目標 170） | 116 → 111 | 128 → 112 | ❌ 略降 |

三件事要記住：

1. **解析度掉了是因為拍攝模式不同。** 舊照片 5046×7670（200MP 模式裁切），
   新照片 1948×3124（12MP 模式裁切），EXIF 同一支 Galaxy S24 Ultra。
   9-11 量到小寫假名在舊照片約 40 px 高，縮到 2.4 分之一只剩約 **16 px**，

2. **「加光」不會讓紙面亮度上升。** 手機自動曝光把畫面往中灰拉，
   補光只會換來更快的快門，記錄下來的紙面亮度不變——量到的 187/194 就是證據。
   要達到 240 得用**曝光補償（+1~+2 EV）或手動曝光**，不是加燈。
   （同一批的 p41 能有 252，是碰巧過曝，不是拍攝手法。）
3. **藍偏是新出現的問題。** 紙面 B−G 從 −1.9 變 +41.0，彩度從 4.8 變 41.6。
   白平衡偏冷，灰階通道上的筆畫對比被壓低。下次拍要鎖白平衡或事後校正。

## 五、結論與下一步

**照片品質（具體是銳利度）確實是原因之一，方向證實。** 關鍵在於：這 2/9 與那批
部分改善，是在**解析度只剩 1/6、曝光沒改善、又多了藍偏**的情況下拿到的——
四項條件只做對一項就有正向結果且零退步，條件補齊的上限應該明顯高於 2/9。

所以**還不到決定 41 頁的時候**，先用同樣兩頁做第二輪，把另外三項補上：

1. **用 200MP／高解析模式**（與舊照片同一個模式），不要用預設 12MP
2. **曝光補償 +1~+2 EV**（或手動曝光）讓紙面接近純白，不是加燈就好
3. **鎖定白平衡**（或用暖白光源），消掉藍偏
4. 保持第一輪已經做對的：相機固定、鏡頭與頁面平行
5. 背面墊黑紙照舊（鬼影本輪無法單獨評估，藍偏把色彩訊號蓋掉了）

第二輪跑法與第一輪相同，成本約 3 分鐘：

```bash
uv run python scripts/ab-photo-quality.py \
    --page 22=/path/new_p22.jpg --page 19=/path/new_p19.jpg --measure-only   # 先確認達標
uv run python scripts/ab-photo-quality.py \
    --page 22=/path/new_p22.jpg --page 19=/path/new_p19.jpg
```

若第二輪修好過半（5/9 以上），再依〈若決定全部重拍〉那節的成本評估動 41 頁。
若條件全部達標仍停在 2/9 上下，那就是 GLM-OCR 在小寫假名這個尺度的上限，
改走 `verify` 對照影像或抽取端的假名拼寫合法性檢查。

## 三、原因是後製，不是拍攝

截斷量測（版心中央 40%）：

| | 純黑（≤2） | 純白（≥253） |
|---|---|---|
| 舊 | 0.00% | 0.00% |
| 一輪 | 0.00% | 0.00% |
| 二輪 | **1.40% / 2.64%** | **1.95% / 2.02%** |

「對比度拉到最高」把灰階過渡截掉了。注音假名本來就印得淡、筆畫細，
**被截掉最多的正是它**。三組裡表現最好的一輪，恰好是唯一沒有後製、
只把對焦拍對的那組。

> **教訓：拍攝端該做的是對焦與打光，後製不要動對比與 levels。**
> 這條與 `image_prompt_template.md` 的〈實測否決的調整〉同性質——已實測，不要再試。

## 四、這些差異都不是呼叫抖動

`control` 與 `control_rep2`（同影像、兩次呼叫）四項指標完全相同；
`round1` 事後重建的數字與第一輪原始跑的也完全相同（128/11/15、105/3/7）。
**GLM-OCR 在同一影像上近乎決定性**，所以組間差異全部歸因於照片。

## 五、真正該做的事：那 65 筆的正確答案早就在手上

照片路線的天花板是 **2/9（22%）**，而且要換來 41 頁重拍 ＋ 約 14 小時重跑
＋ `card_id` 唯一性檢查的手動前置手術。**不值得。**

而 `scripts/check-card-quality.py` 的 `check_marks()` 是這樣判定的：

```python
auto = analyse(front)              # SudachiPy 從漢字詞目推出讀音
if flatten(auto) == flatten(reading):   # 只差濁點／小寫假名
    out.append(...)
```

**正確讀音是分析器算出來的，不是從影像讀的。** 而且判定條件極緊——
兩者「去掉濁點與小寫假名後完全相同」才會報，所以卡片這側幾乎必然是錯的
（docstring 原話）。65 筆全部落在這個條件裡。

也就是說：**這 65 筆可以直接用分析器的讀音修掉，一張照片都不必重拍。**
成本是寫一個修正腳本（分鐘級），而不是 14 小時。

多音字誤修的風險很小：分析器分析的是 `front` 本身，而條件限定「僅差濁點／
小寫假名」——`清く`（きよく，正確）不會被報，因為分析器對 `清く` 也給 きよく。

### 建議的下一個 task

1. 寫一支修正腳本，把 `marks` 這 65 筆的 `reading` 換成分析器的讀音，
   並同步 `tts_front_text`（它是從 `reading` 來的，不同步會被 `fields` 檢查抓到）
2. **不重跑任何階段**——只改讀音欄位，不動 `raw_text`、不重新抽取、不重生媒體
3. 修完再跑一次 `check-card-quality.py`，確認 `marks` 歸零且 `fields` 沒變多

目前 605 張卡共 109 筆待確認：`glyph` 13、`bytes` 5、**`marks` 65**、
`fields` 2、`reading` 24。修掉 `marks` 等於一口氣清掉 60%。
