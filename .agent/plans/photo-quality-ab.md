# 實驗：重拍照片能不能修好「小寫假名與濁點讀不出來」

建立日期：2026-09-11
狀態：**待執行**（等使用者重拍 p22、p19）
腳本：`scripts/ab-photo-quality.py`

---

## 要回答的問題

**照片品質是不是 OCR 讀不出小寫假名與濁點的原因？**
是的話值得把 41 頁全部重拍；不是的話重拍是白費工，該把力氣放在別處。

---

## 已知的事實（2026-09-11 量測，不必重做）

### 1. 錯誤源自 OCR，不是抽取階段

65 筆 `marks` 類讀音錯誤中，**61 筆（94%）的正確讀音從未出現在該頁 `raw_text`**。
OCR 就沒讀到。（另外 4 筆是 OCR 讀對、抽取階段改壞的，與照片無關。）

### 2. 錯誤形態高度集中

```
がいろじゆ ← がいろじゅ      きゆう   ← きゅう
かつりよく ← かつりょく      きよか   ← きょか
きみよう  ← きみょう        きょきょう ← ぎょぎょう（濁點漏掉）
```

全部是**小寫假名被讀成大寫**與**濁點消失**——差別只在字的大小與兩個小點。
這是細節解析不足的典型指紋。

### 3. 解析度不是瓶頸

| | 量到的值 | OCR 通常需要 |
|---|---|---|
| 文字行高 | 243–259 px | — |
| 假名注音字高 | 約 60–80 px | 20–30 px |
| 小寫假名字高 | 約 40 px | 20–30 px |

**再加像素不會有幫助。** 41 頁全部在 23–42 MP。

### 4. 但頁與頁之間的品質差異，預測不了錯誤數

| 指標 | 與 `marks` 錯誤的相關係數 |
|---|---|
| 文字區銳利度（原始解析度） | −0.27 |
| 筆畫對比 | −0.28 |
| 糊邊比 | −0.16 |

而且**最銳利的 1/3（14 頁）平均 1.6 筆錯誤，最模糊的 1/3 平均 1.2 筆**——方向反了。

**原因是這批照片太一致**：糊邊比 40 頁落在 0.48–0.69 的窄帶內，
資料裡沒有「好照片」可以對照。所以**現有資料證不出也否證不了**照片假說，
只能人工重拍幾頁做對照。

### 5. 分塊修好後 OCR 的貢獻已大幅提升

卡片 `reading` 能在 `raw_text` 找到的比例：**28% → 74%**
（28% 是 CLAUDE.md 記的分塊前基準 97/342）。剩下的就是這個特定弱點。

## 拍攝條件

量測顯示這批照片有兩處具體缺陷，**同一批裡的 p41 證明這些數字拍得出來**：

| 缺陷 | 全批現況 | p41 達到 | 腳本的門檻 |
|---|---|---|---|
| 曝光不足，紙面偏灰 | 紙面亮度中位數 **190**/255 | **252** | 240 |
| 筆畫對比低 | 中位數 **130** | **199** | 170 |

另外**每一頁都有背面文字的紫色鬼影**（背面透光），那會給 OCR 加上不存在的筆畫。

重拍 **p22 與 p19** 這兩頁，條件：

1. **光線加足**，讓紙面接近純白（目標亮度 240+）。這同時解決曝光、快門與景深
2. **頁面下墊一張黑色不透光紙**，擋掉背面透光
3. **相機固定**（腳架，或撐在桌面／書堆上），鏡頭與頁面平行，避免手持晃動
4. 其餘不變：同一本書、同樣的框取範圍、不要裁切

> 為什麼選這兩頁：p22 有 6 筆、p19 有 3 筆 `marks` 錯誤，是全書錯誤最密集的兩頁
> （p9 有 8 筆但那頁的錯誤形態較雜）。共 9 個目標，樣本夠小又夠看得出差別。

## 執行

```bash
uv sync --all-extras          # 版面偵測與 OCR 都要

# 先只看照片本身有沒有拍得比較好（不呼叫 OCR，幾秒鐘）
uv run python scripts/ab-photo-quality.py \
    --page 22=/path/to/new_p22.jpg \
    --page 19=/path/to/new_p19.jpg \
    --measure-only

# 紙面與對比都達標之後，跑完整實驗
uv run python scripts/ab-photo-quality.py \
    --page 22=/path/to/new_p22.jpg \
    --page 19=/path/to/new_p19.jpg
```

**`work/cards.csv` 一個位元組都不會改**——實驗自己在 `work/ab-photo-quality/`
底下建工作檔。

### 腳本會做的事

1. 量測新舊照片的紙面亮度、筆畫對比、銳利度，未達標會標 ⚠
2. 從 `check-card-quality.py` 取出這兩頁目前的 `marks` 錯誤，當作目標讀音
3. **同時重跑舊照片與新照片**——控制組跑舊的，是為了排除「這次呼叫剛好不同」；
   拿新照片去比存在 CSV 裡的舊 `raw_text` 會把兩個變因混在一起
4. 逐筆報告目標讀音有沒有出現在 `raw_text`，並給判讀

## 怎麼讀結果

| 結果 | 判讀 | 該做的事 |
|---|---|---|
| 修好 > 一半（5/9 以上） | 照片是主因 | 依同樣條件重拍全部 41 頁，重跑 `ocr` → `extract` → 下游。成本見下 |
| 修好 = 0 | 是 GLM-OCR 在這個尺度的上限 | **不要重拍。** 改從別處補救：`verify` 對照影像修 `reading`，或在抽取端加一條假名拼寫合法性檢查（`ゆ/よ/つ` 出現在拗音位置就是可疑） |
| 介於中間 | 部分有效 | 重拍 41 頁的成本對修復率值不值得由使用者判斷；也可以只重拍錯誤集中的幾頁 |
| 反而壞掉 > 修好 | 重拍的條件改壞了 | 檢查是不是過曝（紙面 255 會把細筆畫吃掉）或對焦跑掉 |

### 若決定全部重拍，成本參考

以 2026-09-10 那次 28 頁重跑實測外推 41 頁：

| 階段 | 預估 |
|---|---|
| `ocr` | 約 30 分 |
| `extract` | 約 5 小時（一頁 6.7–8.1 分） |
| `scene` | 約 4 小時（約 600 張 × 25 秒） |
| `prompt` | 約 10 分 |
| `image` | 約 5 小時（30.6 秒/張） |

**加上必要的前置手術**：`extract` 重跑同一頁會撞 `card_id` 唯一性檢查
（見 `stages/extract.py` 模組 docstring），必須先手動移除舊卡片列並搬走媒體。
作法照 `logs/2026-09-10_fix_ocr-chunk-rotation.md`〈資料重跑（28 頁）〉那一節。
