### 2.1 GLM-OCR 的 prompt 規格（使用者提供）

GLM-OCR 只支援兩種 prompt 場景，**不接受自擬指令**：

1. **Document Parsing**——從文件擷取原始內容，任務前綴固定：
   ```
   text    → "Text Recognition:"
   formula → "Formula Recognition:"
   table   → "Table Recognition:"
   ```
2. **Information Extraction**——擷取結構化資訊，prompt 必須內嵌嚴格的 JSON schema
   （例：`请按下列JSON格式输出图中信息:` 後接 schema 本體），輸出須嚴格符合該 schema。

本專案的 `OCRAgent` 屬第 1 類，用 `Text Recognition:`。**不走第 2 類**——結構化抽取是階段 ②
`ExtractAgent` 的職責，OCR 階段只負責出純文字（與 phase-2-ocr.md「OCR 不設 `output_schema`」一致）。

### 2.2 真實書頁的模型比對（`tests/fixtures/pages/page_01.jpg`）

輸入：原圖 4000×3000 = 12,000,000 px，**超過 GLM-OCR 宣告的 `max_pixels` 9,633,792**，
等比縮至 3200×2400 = 7,680,000 px（base64 2.37 MB）後送出。比對基準為
`tests/fixtures/ocr_raw/page_01.txt`。

| 面向 | GLM-OCR `Text Recognition:`（9.1s） | Gemma 4 直讀（關思考後 17.4s／542 tok） |
|------|--------------------------------------|------------------------------------------|
| 標題詞 | 13 條中 12 條正確（`増大` 誤讀為 `そうだい`） | **幻覺**：生出頁面上不存在的 `壮大`、把 `予算が多そうだ` 當標題 |
| 讀音 | 多數正確，但振假名與本文黏連（`だん匯う そうち`、`のうりくそうとう能力相当の地位`） | `送別`→`そうび`、`属する`→`らくする`，錯得離譜 |
| 釋義 | 忠實照抄頁面上的中文 | 自行改寫為 `[意味]／[例文]` 格式，內容為模型自編的日文 |
| 其他缺陷 | 掉字（`体力を測定する` 少「体力」）、句尾偶有重複 | 混入韓文（`纷纷 입장`）、誤譯（`虎はネコ科に属する`→「屬於老虎科」） |

**結論**：Gemma 4 在密集排版的真實書頁上不是在 OCR，而是看圖說話；GLM-OCR 雖有振假名黏連
與偶發掉字，但忠實度遠高。→ Q1 維持 `two_stage`。

### 2.3 Gemma 4 的 thinking 必須關閉（新發現，影響 agents.yaml）

`gemma4_31b_q4_K_M-optimized` 的 capabilities 含 `thinking`，預設開啟。實測讀整頁影像時
**4096 個 completion token 全被思考吃光**，`finish_reason=length`、`content` 為空字串，
思考內容落在 `message.reasoning` 欄位。

關閉方式（兩者實測皆有效）：

| 方式 | 端點 | 結果 |
|------|------|------|
| `reasoning_effort="none"` | OpenAI 相容 `/v1` ✅ **本專案採用** | `reasoning` 歸零、`content` 正常 |
| `"think": false` | Ollama 原生 `/api/chat` | 17.4s／542 tok、`done_reason=stop` |

agent_factory 走的是 `/v1`，因此用 `reasoning_effort`。`VisionExtractAgent` 的
`model_params.params` 必須帶此設定，否則影像路徑會拿到空輸出。

> ⚠️ **需一併查證**：Phase 1 的 `ExtractAgent` 同樣未設此參數。文字抽取在 Phase 1 驗收時
> 通過（structured output 有解析出結果），但長輸入是否可能同樣耗盡預算未經驗證。
> Task 2.5 動 `agents.yaml` 時一併確認並回報，不擅自更動已驗收的設定。

### 2.4 影像尺寸上限（新發現，影響 Task 2.2／2.3）

真實書頁 4000×3000 超過 GLM-OCR 的 `max_pixels`，**縮圖是必要步驟而非最佳化**。
`ocr_client.py` 的 `encode_image_b64()` 需在編碼前依上限等比縮圖，上限值設定化
（預設對齊 9,633,792 px）。Task 2.2 的 DPI 200 也須回頭核算：A4 @ 200 DPI 約
1654×2339 = 3.9M px，在上限內；300 DPI 為 8.7M px，接近上限。

### 2.5 已評估並否決：抽取階段同時送入影像（grounded extraction）

**提案**（使用者，2026-08-22）：既然 GLM-OCR 有掉字與振假名黏連，抽取時把原始影像一併送給
Gemma 4 當參考校正，是否能改善？

**實測 A／B**：同一份 GLM-OCR 文字（`page_01`），A 組純文字、B 組文字＋影像並明示
「衝突時以影像為準」，兩組皆用 `ExtractOutput` schema 與 `reasoning_effort=none`。

| | A 純文字（45.9s／1225 tok） | B 文字＋影像（38.8s／1215 tok） |
|---|---|---|
| 卡片數 | 13（正確） | 13（正確） |
| `増大`／`ぞうだい`（GLM 誤讀為 `□そうだい`） | ✅ 還原正確 | ✅ 同 |
| 振假名黏連 | ✅ 全部修正 | ✅ 同 |
| 幻覺／重複卡 | 無 | 無 |

**逐欄位 diff 後兩組完全相同**（僅 `card_id` 雜訊差異，該欄由 `extract.py` 覆寫）。

**結論：不做。** GLM-OCR 的兩種失誤都已被階段 ② 的上下文推理解決——標題誤讀可由例句中的
漢字還原（`予算が増大する`），黏連的讀音字串本身仍在文字流中。影像進來沒有新資訊可補，
卻要付出設定開關、額外測試路徑與每列的 vision token。

> 保留條件：若日後遇到「例句中也不含該漢字」的頁面，影像校正才有價值。屆時形式應為
> `two_stage` 底下的開關（如 `TWO_STAGE_GROUNDING`），**不新增 `INGEST_MODE` 的第三個值**，
> 以免動到驗收標準。`llm_client` 屆時已支援影像輸入（Task 2.5），補上不難。
>
> 附帶結論：B 組**未引入幻覺**。Gemma 4 有文字錨點時是穩的，§2.2 的亂編發生在無錨點的
> `vision_direct` 情境——這也佐證 Q1 的選擇。

### 2.6 驗收回報的 extract 全流程失敗：診斷與修正（2026-08-23）

使用者以**真實英文單字表**（一頁 94 個條目）驗收 `run-all`，extract 全數
`APITimeoutError`。診斷過程推翻了三個假設，最終發現是五個問題疊加。

#### 根因一：ComfyUI 佔住 VRAM（環境）

```
GPU 24576 MiB
├─ ComfyUI (python3 ./ComfyUI/main.py)   2424 MiB   ← 常駐 7 小時
└─ Ollama llama-server                  20198 MiB
```

Gemma 4 需 21.5 GB，扣掉 ComfyUI 後只能載入 **85~88%**，2.6~3.2 GB 溢出到 RAM，
速度由 34 tok/s 崩至 4~6 tok/s。呼叫 ComfyUI 的 `POST /free` 釋放後即回到 100%，
同一段輸入從 844s 降到 189s。

> ⚠️ **診斷時的誤判**：一度歸咎於 `num_ctx`，請使用者由 16384 改為 8192，
> 反而讓失敗從「逾時」變成「JSON 截斷」（8192 裝不下 system prompt 2844 +
> thinking 3000 + 輸出 3200）。`num_ctx` 只是次要因素，主因是 ComfyUI。

#### 根因二：模型能力邊界（設計）

| 條件 | 結果 |
|------|------|
| 31B、關 thinking、10 或 25 條目 | 都只回 **1 張卡**（約 10~20s） |
| 31B、開 thinking、25 條目 | 844s（VRAM 88%）／189s（100%）但吐壞 JSON |
| 31B、開 thinking、整頁 94 條目 | 逾時；可靠處理量約 **5 條目／次** |

**本地模型面對太多條目不會報錯，而是退化**——壞 JSON 或只回一張卡。因此
`reasoning_effort: none` 這條先前記在 §2.3 的建議**只適用於影像路徑**，
文字抽取關掉思考會直接廢掉。

#### 根因三～五：本專案的三個 bug

1. `extract` 併發取自 `GLOBAL_CONCURRENCY=6`，本地模型序列化執行，
   **逾時計時器在排隊時照樣在跑** → 併發固定 1
2. 長頁面一次送出 → 加入切段（`INGEST_EXTRACT_CHUNK_LINES`，預設 20）
   與**失敗自動對半重試**（下限 4 行）
3. 切段後每段序號各自從 001 起算，`card_id` 唯一性押在模型服從度上會出事
   （實測模型把段落標籤當成 id）→ 改由程式決定性編號

#### 決定：抽取模型改用 E4B

| | 31B | **E4B（採用）** |
|---|---|---|
| 日文 13 條目 | 157s | **88s** |
| 英文 25 條目 | 吐壞 JSON | **63.7s／18 張卡** |
| 英文整頁 94 條目 | 40 分 45 秒／93 張卡 | **6 分 15 秒／98 張卡** |
| 穩定度 | 時好時壞、尾段 `back` 空白 | 每次成功 |

31B 的宣告保留在 `agents.yaml` 註解中，改一行即可切回。

#### prompt 的五處加強（皆由實測打出來，非預想）

1. deck 不得填 `Vocabulary` 這類泛稱 —— E4B 原本全部歸成一類
2. deck 只填**單一中文詞性** —— 原本出現 `名詞/動詞`、`noun_verb`
3. deck 前綴照抄**並保留分類層** —— 修正 1、2 後它把 `英語::基礎` 當成完整 deck
4. 釋義可由知識補全、**`back` 不可留空** —— 純單字表原文沒有釋義，
   模型照〈補全規則〉留空，而 `back` 是 `pack` 的必填欄位
5. 釋義語言規則 —— 原 prompt 從未規定，日文教材照抄原文中文所以沒暴露

#### 釋義語言：已改為顯式任務參數（2026-08-23）

prompt 裡的語言規則對 E4B 無效（輸入全英文時它就跟著用英文）。改為與 `領域`、
`牌組前綴` 同級的**任務參數** `釋義語言`，由 CLI `--card-language` 傳入——
參數區塊就在輸入開頭、緊鄰教材本文，比埋在 180 行 prompt 裡的一條規則有效得多。

實測（英文 94 條目頁）：**釋義含中文 95／95**（改動前 0／98）。

#### 語言問題全部解決：參數槓桿（2026-08-23）

**本次診斷最可複用的發現**：對 8B 模型而言，同一條要求寫在 180 行 prompt 的中段
幾乎無效，提升為**任務參數**（輸入開頭、緊鄰教材本文）就守得住。

| 同一條要求 | 寫在 prompt 中段 | 提升為任務參數 |
|------------|------------------|----------------|
| 釋義語言 | 0／98 | **95／95** |
| 分類語言 | 60／98（25 條目單測 18／18，跨段即崩） | **98／98** |

`分類語言` 預設跟隨 `釋義語言`，使用者不需多傳參數。prompt 中的可選值同時
收窄為**列舉清單**（名詞／動詞／形容詞／副詞／形容動詞／連體詞／接續詞／
感嘆詞／語法／其他），並明文禁止 `Vocabulary` 這類泛稱——列舉比抽象規則好服從。

最終驗證（走完整 CLI）：

| | 日文 13 條目 | 英文 94 條目 |
|---|---|---|
| 卡片數 | 13 | 98 |
| deck 中文 | 13／13 | **98／98** |
| 釋義中文 | 13／13 | **98／98** |
| 空釋義 | 0 | 0 |
| 讀音／例句齊全 | 13／13 | — |

### 2.7 教材通用性：兩個無聲缺陷與分類參數化（2026-08-23）

使用者指出**本工具從未限定語言類教材**（`docs/project-overview.md` 與 prompt 第一條
核心原則皆然），並質疑先前的評估是否被測試教材誤導。以受控實驗回答。

#### 實驗設計：隔離「語言」「領域」「有無釋義」三個變因

| 教材 | 語言 | 有無釋義 | 領域 | 結果（E4B） |
|------|------|----------|------|-------------|
| 日文 N2（既有 fixture） | 日文 | 有 | 語言 | 13／13 |
| 英文·有釋義（新造 10 條目） | 英文 | 有 | 語言 | **10／10、例句 10／10** |
| 藥理學（新造 8 條目） | 中文 | 有 | **非語言** | 8／8 |
| 英文·無釋義（使用者教材 94 條目） | 英文 | **無** | 語言 | 例句僅 4／18 |

**關鍵變因是「有無釋義」，不是語言、也不是領域。** 有釋義的教材，模型做的是
「抽取」；沒有釋義的索引式單字表，模型做的是「生成」——憑知識造釋義、猜詞性、
編例句，本質上更難且無從校對。使用者的教材屬後者，測試素材本身沒有問題。

#### 缺陷一：無聲的產出不足（最危險）

先前所有失敗都會「喊出來」（逾時、壞 JSON、例外），唯獨這一種不會：
**呼叫成功、JSON 合法、狀態 done，7 個條目卻只回 1 張卡**（23 秒交差）。
缺掉的卡片會安靜寫進工作檔，`status` 顯示一切正常。

→ 新增 `estimate_entries()` 與產出檢查：以條目符號（`□`、`■`、`1.`…）估算條目數，
產出不到一半即視為失敗，交給既有的對半重試。實測估算準確（藥理 8／8、
英文 10／10、日文 13／13）；無符號的索引式單字表回 0 → 跳過檢查，不誤判。
刻意只認強標記——`•`、`・` 多為例句或子項，計入會高估而觸發無謂重試。

#### 缺陷二：修語言類問題時把工具收窄了（自己造成）

|------|--------|----------|

**教材屬於哪個領域，只有呼叫端知道**——寫死進 prompt 不是「設定」而是「猜測」。
與 Phase 1 把 `領域`、`牌組前綴` 設計成參數同一個判斷，只是這次繞了兩圈才想通。
不傳時仍依 prompt 的領域範例自行判斷，不會變成必填。

### 2.8 抽取模型的完整評估（2026-08-23）

使用者陸續提供 Qwen 與 Gemma 4 MoE 變體。四種教材、走完整 CLI 的比較結果：

| | **E4B 8B（採用）** | a4b 26B／4B active | Qwen 27.3B |
|---|---|---|---|
| 檔案／VRAM 載入 | 5.4 GB／**100%** | 28.1 GB／73% | 22.4 GB／94% |
| 日文 13 條目 | 13／13、88s | 13／13、106s | 13／13、96.5s |
| 英文·有釋義 10 條目 | 10／10、例句 10／10 | 10／10、例句 10／10 | 10／10、**例句 0／10** |
| 藥理學 8 條目 | 8／8 | 8／8 | 8／8 |
| 英文·無釋義 94 條目 | 101 張、例句 70／101、**6m10s** | 97 張、**例句 97／97**、20m48s | — |
| 分類乾淨度 | ✅ 單一詞性 | ❌ 出現 `形容詞／副詞／限定詞／代名詞` | ✅ |
| 影像支援 | ✅ | ✅ | ❌ |
| 思考 | 開著即可 | **必須關** | **必須關** |

**決定：維持 E4B。** a4b 的例句填充率在無釋義教材上明顯較佳（97／97 對 70／101），
但速度差 3.4 倍（200 頁的書約 20 小時對 69 小時）、分類會違反 `分類選項` 的封閉清單、
且 28.1 GB 在 Phase 3 與 ComfyUI 完全無法共存。

#### 兩個推翻先前判斷的發現

1. **模型大於顯卡容量，對 MoE 不是硬性阻礙**。a4b 有 7.9 GB 在 RAM（載入僅 73%），
   仍達 29~30 tok/s，與完全載入的稠密模型相當——每 token 只啟用 4B 參數，
   被 offload 的層有很高機率不被觸及。先前「llama.cpp 按層 offload，MoE 救不回來」
   的推論是錯的。**選模型時不應只看檔案大小是否小於 VRAM。**

2. **`num_ctx` 變體在「模型大於顯卡」時失去意義**。使用者為 a4b 建了 8K／12K／16K
   三個變體，但 8K 已是唯一可行——KV cache 一大就更擠。同理，Qwen 的 8K／12K
   差異也不顯著。

#### 重試機制的價值獲得驗證

a4b 裸 API 呼叫時，四種教材有兩種隨機截斷失敗（同一份藥理學教材在另一次卻成功）。
但**走完整 CLI 全數通過**——切段與對半重試把這種不穩定完全吸收。這說明本 phase
加入的重試機制不只是為了長頁面，也是模型不穩定時的保險。

### 2.9 索引式教材的補釋義前置步驟（`--enrich`，2026-08-23）

使用者提議：把「無釋義教材」單獨拆成一個切換點，先補釋義再抽取。
實測證實有效，已實作。

#### 問題的形狀

整頁 101 張卡的例句填充呈**塊狀缺失**，非漸進退化：

```
第   1~ 30 張: 27/30
第  31~ 60 張:  5/30   ← 連續三段整段沒補例句
第  61~101 張: 38/41
```

也就是某幾次呼叫「忘了」補例句。單段測試時反而正常（25 條目 18／18），
所以不是能力不足，而是**單次呼叫裡同時做「憑知識生成」與「結構化輸出」時，
生成的部分會被犧牲**——8B 模型顧此失彼。

#### 解法與實測

先經 `EnrichAgent` 把清單補成「條目＋釋義＋例句」的完整教材頁（純文字、
不設 `output_schema`），再交給既有抽取路徑——等於把難教材轉換成實測 10／10
的那條路。

| | 不加 `--enrich` | **加 `--enrich`** |
|---|---|---|
| 卡片 | 101 | 109 |
| 例句 | 70／101（塊狀缺失） | **109／109（每段滿格）** |
| 釋義中文 | 101／101 | 109／109 |
| 耗時 | 6m10s | 9m05s（+47%） |

代價比改用 a4b（慢 3.4 倍、分類違反封閉清單）划算得多。

#### 四個設計決定

1. **放在 `extract` 內部，不新增 pipeline 階段**——新增階段要動 `CardRow`
   狀態欄位與 `STAGE_FIELDS`（狀態機層級）；補釋義在語意上是抽取的前置步驟。
   切段、對半重試、產出檢查全部沿用。
2. **參數而非自動偵測**——自動判斷「有無釋義」不可靠（日文漢字也是 CJK，
   用「有沒有中文」會誤判日文教材）。教材是什麼只有呼叫端知道，同 `--deck-categories`。
3. **產出檢查對照原始輸入**——補釋義若漏掉條目，拿補完的結果當基準就檢查不出來。
4. **補完的結果比原文短即視為失敗**——代表漏抽條目，交給對半重試。

#### 連帶修正：Protocol 容納純文字 agent

`LLMClient.run_agent` 在 Phase 1 寫死「非 structured output 就報錯」——當時所有
LLM agent 都有 schema，這是合理的防護。但 `EnrichAgent` 刻意不設 schema
（與 `OCRAgent` 同類），被自己的防護擋下。

改為讓 Protocol 反映 agent_factory 本來就有的兩種模式（有 schema 回 model、
無 schema 回字串），型別檢查移到呼叫端——`ExtractStage._call` 拿到字串仍會拒絕，
因為抽取一定要 structured output。防護還在，只是移到正確的層級。
依 architecture.md：「規格補齊後若與此處不符，調整 Protocol 而非上層邏輯」。

### 2.10 vision_direct 的 max_tokens 與補釋義的自動判斷（2026-08-24）

#### vision_direct 全數 `Invalid JSON`

根因是 `VisionExtractAgent` 的 `max_tokens: 4096`：

| | finish | completion | 結果 |
|---|---|---|---|
| `max_tokens: 4096` | **length** | 4096 | 13904 字的殘缺 JSON ❌ |
| 不設上限 | stop | 14257 | 74 張卡 ✅ |

**影像路徑無法切段**（圖不像文字能切開），一頁 94 個條目的輸出必須一次吐完，
一萬多 token 撞上 4096 就被腰斬。該上限是 Task 2.5 時從 `OCRAgent` 抄來的——
但 OCR 的輸出是一頁文字（數百 token），抽取的輸出是數十張卡的 JSON，量級差一個
數量級。**複製設定前要先確認兩者的輸出量級是否相當。**

> 仍存在的固有限制：影像路徑對密集頁面會產出不足（實測 74 張／94 條目，
> CLI 端到端為 30 張），且無切段可補救。`two_stage` 仍是預設且品質較佳。

#### 補釋義改為自動判斷（使用者要求，方案 B）

`--enrich` 原為手動旗標。改為 `MaterialTypeAgent` 判斷——獨立一次短呼叫，
只輸出 `HAS_DEFINITIONS` / `NO_DEFINITIONS`。

選擇「獨立呼叫」而非「抽取時順便回報」的理由：後者太晚（抽完才知道要重跑）；
而**判斷與生成分離**正是 §2.9 學到的教訓。成本可忽略——每列一次、只送前 40 行、
輸出一個詞，實測每次 0.8~1.4 秒。

四種教材的判斷準確度：**4／4**。

過程中修的兩個問題（皆為已知模式的重演）：

1. `max_tokens: 16` 被思考吃光 → 兩組回空字串。判斷任務不需要思考，
   補 `reasoning_effort: none` 並放寬到 32。**同一個坑本輪已踩第四次**
   （Gemma 31B 讀影像、Qwen、a4b、此處）。
2. 日文教材誤判為「沒有釋義」→ 抽象判準對 8B 模型不夠，補上具體範例後修正。
   另補一條界線：**讀音、詞性標記、例句都不是釋義，但它們的存在也不代表沒有釋義**
   ——日文教材正是因為讀音與詞性標記太顯眼而被誤判。

介面：`enrich` 由 `bool` 改為 `bool | None`，`None`（預設）自動判斷；
CLI 提供互斥的 `--enrich` / `--no-enrich` 作為覆寫。判斷失敗時**保守地不補**
——多花一次呼叫事小，把已有釋義的教材重寫一遍可能覆蓋原文。
vision 路徑在判斷之前就返回，不會為空的 `raw_text` 付一次無謂呼叫。
